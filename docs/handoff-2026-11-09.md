## 1. What Solera is

From the README: "A Python data orchestrator: assets declare outputs, partitions, inputs, and placement; a durable control plane plans and executes runs; every committed output is an immutable ref." All engine state lives in SlateDB on object storage (local files or S3), so it needs no external service. Relational outputs can live in Postgres. It is an experimental alpha, aimed at real use in Erwin's own applications (Monolith, red-metal).

The parts of the repo:

| Path | What |
|---|---|
| `python/solera` | The SDK (`@asset`, `Output`, `Incremental`, partitions, triggers) and the key index (`solera.keys`) |
| `python/solera_server` | The engine, state layer, FastAPI, CLI and the built console. The planner is `owed.py` |
| `python/solera_worker` | The worker that runs attempts |
| `native` | The Rust crate behind `solera._native`, which encodes, decodes, sorts and merges the key index |
| `apps/console` | The web console (React, TanStack, Base UI). The built bundle is committed |
| `docs/` | `architecture.md` is normative. `behaviors.md` is the behaviour contract that every design must keep (IDs like INC-4, ENG-8). The rest are design docs per part |

**The key index**, in one line: for each keyed output, it records which keys changed at which commit. That lets an incremental consumer process only what changed since its last batch. Most of the design discussion is about this index and the "progress" each consumer keeps against it.

### 3.2 The running example

Every example uses the design's cast:

```
feed ─▶ items ─┬─▶ tally     keeps a count of items' keys
               ├─▶ copy ─▶ archive
               └─▶ checks    per-key: one call per key
```

`items` gets four commits. A version is named after the commit that wrote it, so `k2@2` was written by c2.

| Commit | Changes |
|---|---|
| c1 | k1, k2, k3 added @1 |
| c2 | k2 1→2, k4 added @2 |
| c3 | k3 removed, k5 added @3 |
| c4 | k1 1→4 |

`tally` reads `items` two keys per batch.

### 3.3 The shift in one table

| | Today | Proposed |
|---|---|---|
| What the index stores | Each key's newest state, plus the commits where it was added or removed | Every change, as `(key, commit, new version, replaced version)` |
| What the index can answer | "What changed since P", and only at a head a batch pinned | `diff(C1, C2)` between any two retained commits |
| A consumer's progress | Key ranges, relabeled to the newest head at every batch commit (the "fold") | **Pieces**, which are key ranges that keep the commit they were read at, plus **points**, which are per-key exceptions |
| Staleness | Computed when asked | Exact owed counts, updated at each commit |
| Stores | Two kinds (immutable, fenced), with fences, repairs and replans | One contract: a write returns the keys it wrote, a load returns the versions it read |

**Progress example.** In run 1, tally's batch 1 at c1 takes k1 and k2, and batch 2 at c2 takes k3 and k4.
- **Proposed:** progress is `(−∞, k2] at c1` and `(k2, +∞) at c2`. That's two ranges, however many keys there are.
- **Today:** at batch 2's commit, the first range is relabeled to c2. k2 changed at c2 inside that range, so it becomes a point: "k2 present, at a version since replaced". The relabel costs index reads during the commit, and the point keeps old history alive.

### 3.4 The 14 questions

These match the panel's Q1–Q14 one for one. Each recommendation is the coordinator's, unless it says otherwise.

#### Q1. The core proposals (multi-select; all recommended)

**P1. Each entry stores the version it replaced.**
- **Today:** the index holds each key's newest state. It knows k1 changed since c1, but not what k1 was at c1.
- **Proposed:** the c4 entry reads `k1: 1 → 4`.
- **Example, a revert:** feed's k1 goes v1 → v2 → v1 before items runs. Today items gets k1 as `updated` and reprocesses it (INC-4). With P1, `diff(f1, f3)` sees v1 at both ends and delivers nothing.
- **Cost:** about none. The engine already computes the replaced version at commit, and today it uses it only for cleanup.

**P2. One index for planning and history.**
- **Today:** the index serves planning only. Per-key lineage ("what exactly did batch 3 receive?") isn't built.
- **Proposed:** the same files answer "what's owed now" and "what did tally's run 2, batch 1 get". The second is `diff(c1, c4)` over `(−∞, k2]`, which gives k1 1→4 and k2 1→2.
- **Rejected alternative:** a lean head-only index plus a separate history archive. It stores everything twice, and the two copies can drift apart.
- **Cost:** a consumer a month behind reads every change a hot key had that month. A key updated 1,000 times means 1,000 entries to read, not 1.

**P3. Keep today's 4× merge rule.** No change. A merged layer holds at most 4× the bytes of all newer layers (+1 MiB), so any reader reads at most about 5× what changed.

**P4. No fold.**
- **Today:** every batch commit relabels the older ranges, as in the example above.
- **Proposed:** a batch commit overwrites its own range and nothing else. `(−∞, k2] at c1` stays at c1 until a batch covers it again, and then `diff(c1, head)` finds k2.
- **Cost:** pieces can pile up, at most one per batch until the next run sweeps them together. In the worst case, a 10,000-batch run racing upstream commits leaves 10,000 pieces, about 1 MB.

**P5. Points carry explicit versions.**
- **Today:** points made by the fold say "at a version since replaced". That only means something while the index still holds that commit.
- **Proposed:** points are always explicit. A key k7 that fails forever keeps `k7 → v1`, so it never forces the index to keep old commits.

**P6. Each attempt plans at its own head.** This is today's behaviour.
- **Example:** attempt 1 plans at c4, takes k1 and k2, and fails. Then c5 lands. The retry plans at c5 and may take k1 and k3 instead.
- **Why it's listed:** only in-flight attempts ever read old data files, so cleanup only has to look at live attempts.

**P7. A full run's reset is one "clear" commit.**
- **Today, keyed outputs:** a full run writes one removal per key, which is 100M entries at 100M keys.
- **Today, unkeyed outputs:** a reset starts a new "life", and the consumers start over too (INC-13). One full run cascades down the graph.
- **Proposed:** the full run's first commit carries one flag, "everything before is removed", and then the rebuilt keys. Commit numbers continue, and downstream keeps its progress.
- **Example:** copy runs full in two batches. copy#2 is the clear plus k1 and k2, and copy#3 adds k4 and k5. archive sits at copy#1 and gets one diff: k1, k2 and k4 updated, k3 removed, k5 added.

**P9. Progress records successes only.**
- **Today:** a failing key counts as processed at the version it failed on, and its failure record drives the retries.
- **Proposed:** the consumer still holds the old version, and a point records that. If checks' k2 fails on v2, the point is `k2 → 1`. k2 is then **owed but not due** until its retry time, so it doesn't make checks look stale.
- **Example 1:** items adds k6, checks fails on it, then items removes k6. Today k6 counts as processed, so checks owes a removal of a key it never produced. Proposed: nothing is owed, and the failure goes away.
- **Example 2:** k2's input goes back to v1 before the retry. The failure no longer matters, so there's no retry.
- P9 is also what makes the amended P8 (Q2) possible.

**P11. Paused consumers: a single cut now, "preserved commits" later.**
- **Today:** a consumer whose position has fallen below what the index keeps gets a full run. CLN-11 isn't built.
- **Proposed, migration step 5:** the index never drops what a live piece needs. tally, paused 40 days under a 30-day window, catches up with one diff (k2 updated, k3 removed, k4 added), with no full run.
- **Cost:** the index keeps every entry since the pause. A key that changed 10,000 times while tally slept is 10,000 entries.
- **Later, step 9, once that cost shows up:** below a horizon, keep only the states at commits someone still points to. That key then costs one entry.

**P12. Downstream waits while upstream is midway through a full run.**
- **Today:** there is no gate. Here is copy's full run from P7, seen from archive:

  | | What archive processes |
  |---|---|
  | No gate, at copy#2 | k1, k2 updated; **k3, k4 removed** |
  | No gate, then at copy#3 | **k4 added**, k5 added |
  | With the gate, one diff after copy#3 | k1, k2, k4 updated; k3 removed; k5 added |

  Without the gate, archive removes k4 and adds it back, and its output lacks k4 in between.
- **Cost:** if a full run is canceled midway, downstream stays held until someone reruns the upstream. The status says "held: upstream incomplete (copy)". Each input can opt out if it wants partial data.

**P13. Source loads report what they found (sources only).**
- **Today:** the log says `report.xlsx@v2`, and the batch loads v3. Only the consumer records v3, as a point. The log still says v2, so the key looks owed forever and every run re-reads it.
- **Proposed:** the source's log also records v2 → v3, unless the log changed that key after the batch planned. Other consumers learn about v3 too.
- **Side effect:** loads now move a source's head too. So a sensor tick that finds the source changed under it is refused only for the keys that changed, not as a whole (SRC-10).
- This applies to sources only. Produced outputs are P16's case. (W65's review showed that extending P13 to produced outputs would launder late or dead writes into the log.)

**P14. Exact owed counts, kept current.**
- **Today:** "is tally stale, and by how much?" is computed on request, by one comparison, and cached until something changes.
- **Proposed:** each piece keeps the exact number of keys it owes, adjusted by each upstream commit's entries. Most entries cost nothing to count. A key that changed again since the piece's commit costs one index lookup.
- **Example, a revert:** items is in sync with feed at f1, owing 0. At f2, k1 goes v1→v2, so the count goes to 1. At f3, k1 goes back to v1, so the count returns to 0. No run starts. items was correctly stale only between f2 and f3.
- **Example, an excluded key:** copy takes only `k*`. If items commits only `x1`, copy's count doesn't move.

#### Q2. P8: a per-key asset's definition change or full run (Erwin flagged this as inefficient)

**Today, and as the design doc still drafts it:** progress resets to `held`, which means "the consumer holds whatever its output holds, at unknown versions". Each batch then scans both items and checks' own output, and compares them:

| Key | In checks' output | In items | Planned as |
|---|---|---|---|
| k1 | yes | yes | updated |
| k3 | no | yes | added |
| x9 | yes | no | removed |

**Amended (recommended):** with P9, progress already describes checks' output exactly, so nothing needs resetting.
- The pieces keep the old definition, which differs from the new one, so every key they cover is owed.
- The same classes as in the table above then come from progress and items' index alone.
- What goes: the scan of checks' own output and the special `held` state. Each key also keeps the upstream version it was built from.

`held` would stay only for progress that can't be trusted: an upstream deleted and recreated, state migrated in from elsewhere, or a store repaired by hand.

#### Q3. P10: should successful keys' durations be stored?
- **Today:** `key_outcomes` logs every call of a per-key asset, ok included, with its duration. A 100M-key full run writes 100M rows.
- **Proposed (recommended):** store only failures, with their durations. Which keys succeeded is derived from lineage, and each batch stores a duration histogram.
- **What you'd lose:** "how long did k123 take the last time it succeeded?" Every failure, and each batch's p50 and p99, remain.
- **A middle option the coordinator offered:** also keep each batch's 10 slowest keys. That's 0.1% of the rows at 10k keys per batch, and it still answers "which key made this batch slow?".

#### Q4. P15: should stores that overwrite in place refuse older versions?
- **Today:** Postgres is a "fenced" store, which takes a lot of machinery:
  - A writer must acquire the fence, and a stale writer's write is refused (STO-4).
  - A dead writer starts a repair clock, and readers wait (ENG-8).
  - A read that sees a newer commit makes the batch replan (STO-3).
- **Settled (D184):** one store contract, and all of that machinery goes.
- **P15 adds one rule** for stores that overwrite in place: a write never goes back in versions. In SQL that's `WHERE excluded.version > t.version` on the upsert. In a key-value store it's a conditional put.
- **Example:** attempt A (version 6) writes k2@6 and stalls. The engine gives up on it, and the retry B (version 7) writes k2@7 and commits. Then A's late write arrives, and it's refused because 6 < 7. Without P15, the row silently goes back to k2@6 while the log says 7.
- **Contract (recommended) or recipe:** as a contract, every store must implement it, including ones users write, and the conformance tests check it. As a recipe, stores that skip it lose "nothing goes back in time" (INC-8), along with ENG-7 and CLN-3.

#### Q5. P16: a version that no commit ever recorded

**The case P15 can't block:** attempt A (version 6) writes k2@6 and dies before committing, so the log still says k2@2. If the retry no longer plans k2, the row stays at k2@6. It's the newest version, so P15 lets it stand.

**Today:** the repair clock reruns the partition, and readers wait (ENG-8).

**Proposed (recommended):** the engine assigns every version and knows which attempts committed, so it can tell that k2@6 is bogus.
- As soon as an attempt dies after it may have written to an in-place store, the engine marks its keys owed again on items. For a per-key producer that's the key itself. For an ordinary producer, the retry redoes the dead attempt's whole range, every key in it.
- If tally loads k2@6 before that repair lands, the engine raises an alarm naming items, k2 and attempt A. tally keeps k2@6 as a point and stays owed k2 until items rewrites it.
- `k2: 2 → 6` never goes into items' log.

**The alternative, treating it as a fact and writing it into the log,** goes wrong on a store without P15, as the review showed:
1. A's late write sets k2 back from 7 to 6.
2. tally's load reports it, and the log records `k2: 7 → 6`.
3. Downstream processes an "update" to older data, and nothing ever repairs it.

#### Q6. "Upstream incomplete" without a number
- **Example:** copy is one batch into a 10,000-batch full run, and archive's progress predates copy's clear.
- A count for archive would cost one index lookup per rebuilt key (up to 100M), for an edge that P12 is holding anyway.
- **Proposed (recommended):** archive's reason reads "upstream incomplete". It's exact, just not a count. When copy finishes, one scan gives the exact count.

#### Q7. How long do append-only outputs keep their data?
- **Example:** `events` appends records with each commit, and `digest` reads it incrementally. Retention matters when digest runs full, because it rebuilds from whatever events still holds.
- **Today:** there's no rule. Fable's brief flagged it as open.
- **Option 1 (recommended):** keep everything forever by default, with an optional retention per output that drops the oldest batches. You opt into losing data.
- **Option 2:** match the asset's run retention. A 7-day run history would then silently delete week-old data.
- **Option 3:** keep it until every current consumer has processed it. A consumer added later, or any full run, then sees only a recent tail, and what it sees depends on when other consumers happened to run.

#### Q8. The index's file format

D183 said "decided by benchmark", and the benchmark (T44, W57) didn't decide it. Hence the question. (§4 of the design doc still calls the format "Settled (D183)". It should be reworded once Erwin picks.)

- **Today:** our own block format, read and written by the Rust extension (`docs/key-index-format.md`).
- **The benchmark, at 100M keys, across 1,264 measurements:** the two formats are within about 10% of each other on the index's own reads.
- **For Parquet:** files are 10–12% smaller, and DuckDB can query history straight from them (2–160 ms per query, against 0.35–0.56 s for ours through an Arrow export). W57 recommends Parquet.
- **For our format:** a half to a third of the S3 requests, scattered lookups 1.7–2× faster, about a fifth of the metadata (1.8 MB against 10 MB per 100M keys), and no new dependency. Parquet would add 5.7 MB to the native module and 34 s to a clean build.
- **Coordinator's lean:** our format, with a DuckDB table function over our reader for history queries. That function hasn't been measured. Erwin's earlier instinct also leaned away from Parquet, but he asked for measurement over instinct.
- With either format, the engine reads through our own reader. The stock Parquet reader cost 2–5× more (D185).

#### Q9. Should a deploy that changes patterns fire OnChange?
- **Example:** tally has `include=["k1"]` and an OnChange automation. A deploy widens the pattern to `"k*"`, so tally now owes k2 and k3 as adds.
  - **Fire:** the automation runs right after the deploy and adds them.
  - **Don't fire:** tally shows stale ("input changed") until items commits again or someone runs it.
- **Today:** the docs contradict each other. D34 calls a pattern change an asset change, which fires. D140 later made it an input change, which only marks stale. `behaviors.md` lists the question as open.
- **Recommended: fire.** The deploy is the change, and an author who set up OnChange expects it to react.

#### Q10. A removed dynamic partition's data
- **Example:** `sites` drops `west`. Today `site_files[west]` stops getting runs and stops being read, shows `removed`, and its last head stays readable (PAR-6). Nothing says whether its data is ever deleted.
- **Options:** keep it readable for the asset's retention window, then clean it up like any old version (recommended); keep it forever; or delete it at once.

#### Q11. Is store config part of an asset's definition?
- **Example:** you rotate a Postgres password, or point the DSN at a new host holding the same data. If config were part of the definition, every asset on that store would owe a full run.
- **Today:** the code already says no. The definition includes the store's version but not its config, and moving an output to a different store resets it. One doc (`observed-set.md`) says the opposite.
- **Recommended:** config belongs to the deployment. If a change really alters the data, bump the store's version.

#### Q12. Decisions taken without Erwin (multi-select approval)
- **D186:** the planner fix landed before the redesign. The planner read the whole key space for each batch of a full or far-behind run, which took 706 s per batch at 10M keys. Now a batch costs only its own keys: at 100M keys, plans of 10k keys take 1.9–3.4 s (p50). Behaviour is unchanged. Its independent review found one latent cache bug, which is on `main` and fixed on a branch, and some cost fixes that didn't converge (§4.1).
- **D178:** a batch's keys are read from its attempt spec at commit instead of being copied into the journal, which saves about 600 KB per in-flight batch. A head's list of dynamic partitions is derived from the index, because a stored copy drifted after a repair.
- **D182:** refines D178. The list stays on the head, but the engine computes it at each commit (the previous list plus the commit's entries) instead of the worker. An in-memory cache was rejected because planning reads the list synchronously.
- **D181:** a merge that keeps failing backs off instead of stopping for good. After 3 failures it waits 10 minutes, doubling up to 4 hours, and raises an alarm. `solera merges OUTPUT --clear` retries at once.
- **D185:** the format benchmark read both formats through the same I/O code, so it compares the formats rather than their readers.

#### Q13. Rust
- **Erwin's question:** "Could the engine and most of the worker operate in Rust? Python code is only useful to interface with the user's code."
- **Coordinator's answer: yes, in steps.**
  1. Write the redesign's new core in Rust from the start, behind Python bindings (PyO3): the index, the planner, progress, owed counts and `diff`. Today's engine and its ~30k lines of tests keep working.
  2. Port the server and the worker later.
- **Why it's promising:** T45 found that the engine's event loop is the limit, at 82–90% busy, mostly from about 5 µs per key of Python classification. The index reads are already Rust.
- **The proposed spike:** port today's planner inner loop to Rust and rerun the T45 benchmark (`bench/planning/plan.py`). It would measure the speedup and the cost of crossing between Python and Rust on each batch. Roughly a day for a fresh worker. (The panel's wording says "W39", but W39 is retired.)
- **Options:** start now, alongside the design discussion (the panel marks this recommended); start after the design is settled; or don't. The coordinator's earlier advice to Erwin was to settle the design first. The spike is independent of the design, though, so running it in parallel costs nothing but tokens.

## 6. How to work here

**Erwin's rule for workers (set 2026-10-14):**
- A worker owns its review. It starts its own reviewer and fixes the findings, until one round on the final head is clean.
- It reports once: **done** only after a clean review, otherwise **blocked**, with the open findings or a question.
- Pure analysis needs no review.
- Work reported done before this rule counts as unreviewed unless its report names a clean review of the final head.
- The Initiative's own rule: for high-risk changes (locking, migrations, concurrency, crypto), add one expert second reviewer (Fable 5.1) after the first reviewer passes.

**Erwin's model picks:**
- Opus 5.5 High for general work.
- Sonnet 5.5 for simple, fast tasks.
- GPT-6.1 Sol High as the companion reviewer (W67 used Sol xhigh).
- Fable 5.1 High and GPT-6 Astra Extra High as oracles and advanced reviewers.
- GPT-6 Luna High for cheap summaries.

**The repo:**
- There's no `AGENTS.md`.
- Reviewed work lands directly on `main` (no PRs so far). Spikes and designs go on `exp/…` and `design/…` branches.
- Commit titles are sentences that state the rule the change makes true, with decision and worker refs. For example: "The planner streams: a batch's cost is its batch's, not the key space's (D186)".
- Setup: `uv sync --locked`. It builds the Rust extension, so it needs rustup.
- Python: `uv run pytest -m 'not live'`, with `SOLERA_TEST_DATABASE_URL` pointing at `solera-test-postgres` for the Postgres tests. `uv run ruff check`.
- Console: in `apps/console`, run `pnpm typecheck`, `pnpm build`, `pnpm format:check`, `pnpm contrast` and `pnpm test` (Playwright).
- After landing console changes, run `~/.solera-ui/review.sh update` so the review server shows them.
- Scratch goes in `~/scratch/<your thread id>/`, never `/tmp` (see `~/.bb/AGENTS.md`).

**How Erwin likes the design talk:**
- Self-contained explanations.
- Today vs. proposed, with a concrete example for each.
- No project shorthand left unexplained.
- Recommendations clearly marked.
- Pushback and better ideas welcome.

Assume he hasn't read the design doc. He has worked from the coordinator's summaries, so walk him through it, and don't point him at sections.
